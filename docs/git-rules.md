# Git運用ルール

## 基本方針

- `main` への直接コミット・プッシュは禁止（`/git:push` は main 上では**コミットもプッシュも行わずに中断する**）
- プッシュは生の `git push` ではなく必ず `/git:push` コマンドを使う（唯一の例外は後述の「[機密情報チェック](#機密情報チェックpre-push-フック)」の誤検知時）
- **機能追加** は `feature/<機能名>` ブランチで作業し、PR 経由で main へマージする
- **バグ修正** は `fix/<バグ名>` ブランチで作業し、PR 経由で main へマージする

## コミット & プッシュの手順

上から順に実行する。機能追加・バグ修正・ドキュメント修正のいずれも手順は同じで、**変わるのはブランチ名の接頭辞とコミットメッセージの接頭辞だけ**である。

| # | いつ | 実行するもの |
|---|---|---|
| 1 | 作業ブランチがまだ無い | `/git:branch feature/<機能名>`（バグ修正は `fix/<バグ名>`、ドキュメントのみなら `docs/<ドキュメント名>`） |
| 2 | 実装中 | 随時 `/git:diff` で差分を確認する |
| 3 | 新規ファイルを追加した | `git add <ファイル>` で追跡対象にする。**`/git:push` は追跡済みファイルしかステージしない**ため、これを忘れると新規ファイルがコミットから漏れる |
| 4 | コミットする前 | `/check`（ドキュメント検査 → テストクラス欠落検査 → Release ビルド + テスト） |
| 5 | `/check` が通った | `/git:push "feat: 変更内容の説明"` — コミットとプッシュをまとめて行う |
| 6 | プッシュ済みで、PR がまだ無い | `/git:pr` |
| 7 | PR がある | `/git:merge` — CI 通過とマージ可否を確認して main へマージする |
| 8 | マージ後（任意） | `/git:cleanup` — ただし同じブランチで作業を続ける場合は削除しない（下記「ブランチ運用」参照） |

### 途中から再開する場合

ブランチを使い回していると 1 から始まらないことが多い。次の2つを確認して開始位置を決める。

| 確認すること | 確認方法 | 判断 |
|---|---|---|
| 今どのブランチにいるか | `git branch --show-current` | `main` にいるなら 1 に戻る。main では `/git:push` が何もせず中断する |
| PR が既にあるか | `gh pr list --head <ブランチ名> --state open` | あれば 6 は不要。プッシュするだけで既存の PR に反映される |

同じブランチで PR の作成とマージを繰り返してよい。実際このリポジトリは `feature/rag-pipeline` を複数の PR で使い回している。

## ブランチ運用

- `main` ブランチ: 本番相当の安定コード
- `feature/<機能名>`: 機能追加用（PR 経由でマージ）
- `fix/<バグ名>`: バグ修正用（PR 経由でマージ）
- `docs/<ドキュメント名>`: ドキュメント修正用（PR 経由でマージ）

`/git:merge` はマージ後もブランチを削除しない。マージ済みブランチが溜まってきたら `/git:cleanup` で一覧を確認し、削除の可否を判断する。

## コミットメッセージ規約

| プレフィックス | 用途 |
|---|---|
| `feat:` | 新機能の追加 |
| `fix:` | バグ修正 |
| `refactor:` | リファクタリング |
| `docs:` | ドキュメント変更 |
| `chore:` | ビルド・設定変更など |

例: `feat: PDFからのテキスト抽出を追加`

## 機密情報チェック（pre-push フック）

push 時に [.claude/hooks/pre-push](../.claude/hooks/pre-push) が自動で走る（`/git:init` で登録される）。差分の**追加行のみ**を対象に、APIキー・パスワード・シークレット・アクセストークン・プライベートキー・AWSアクセスキー・接続文字列パスワードのパターンと、`.env` を含むファイル名を検査し、検出されると push をブロックする。

検出されたら、まず出力された該当行を目視で確認したうえで、以下のどちらかで対応する。

| 判断 | 対応 |
|---|---|
| 実際の機密情報だった | 該当箇所を取り除いてコミットし直す。すでにコミット済みなら、push 前に履歴からも除去する |
| 誤検知だと確認できた | `git push --no-verify` で回避してよい |

`--no-verify` を使ってよいのは**目視で誤検知だと確認できた場合に限る**。確認せずに付けるのは禁止（チェックが無いのと同じ状態になるため）。

## 注意事項

- `.env` やシークレット情報を含むファイルは絶対にコミットしない（管理方法は [docs/development-setup.md](development-setup.md) の「シークレットの設定」を参照。push 時のチェックは上記「機密情報チェック」を参照）
- `git push --force` は原則禁止（main ブランチへは特に厳禁）
- プッシュ前に `/git:diff` で変更内容を確認する
